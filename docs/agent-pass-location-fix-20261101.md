# Posting execution and explicit location context

The reported request, `đăng pass lại cái ghế này 500k.`, failed the posting-intent classifier and reached ordinary media chat. The exact phrase was reproduced as a failing unit test before changing the classifier. The fix understands common pass/resale phrasing, keeps ordinary buyer/how-to questions separate, and has a service-level regression asserting that media chat is not called for this request.

Posting now calls a dedicated Gemini JSON-schema generation path with a separate system instruction. It does not rely on the general chat prompt or Markdown formatting. A real provider call using the reported screenshot returned a structured draft with price 500,000 VND. This test is explicitly opt-in and never publishes.

An optional `location` request field accepts explicitly shared coordinates, address, capture time and accuracy. Invalid and older-than-15-minute points are rejected. General chat history does not store this location field. Posting fills location from the established seller address first, a valid current draft second, and then the explicitly shared point; a profile address remains a fallback requiring valid coordinates. Poor GPS accuracy does not automatically populate a posting location. All public posting fields remain visible and editable before approval.

Nearby room requests query actual active non-synthetic native posts and non-expired imported rooms with real coordinates. The query applies known price/area/occupancy/amenity constraints, a 3 km bounding box and final Haversine distance, returns at most eight closest results, and does not claim drive times. Imported rooms with unknown required amenity/occupancy data are excluded rather than asserted to match. Out-of-area, empty, clarification and missing-location states are explicit. Food discovery reuses the existing in-stock marketplace search with the shared location. Neither nearby path sends an order or creates a transaction.

The frontend reads GPS only after pressing the location button, permits manual address selection and forgetting the point, and resumes a waiting location-based read after sharing. A pending posting preview can receive a newly selected location without another model call. The backend still checks Premium before generation and confirmation, and publication still requires explicit approval with idempotent retries.

Validation: exact intent red/green, actual service routing, real provider JSON output, isolated PostgreSQL location fill/nearby/budget/expired/unlocated tests, existing approval concurrency rules, opted-in history tracking, and browser GPS consent/automatic continuation/forget-location/internal-detail navigation. No public production test listing or financial transaction is created.
